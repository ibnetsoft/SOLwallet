## 4. 거래(주문) 관련 버그 수정 — 가장 큰 비중

### 4-1. wSOL 래핑 간헐적 실패 (`409e55a`)
**현상:** SOL 매도 주문 시 "SOL을 wSOL으로 래핑하는 데 실패했습니다" 에러가 간헐적으로 발생.

**원인:** 클라이언트 요청 타임아웃(30초)과 서버의 온체인 컨펌 대기 타임아웃(30초)이 동일하게 설정되어, 서버가 컨펌을 기다리는 동안 클라이언트가 먼저 요청을 포기해버리는 레이스 컨디션. 네트워크가 혼잡한 순간에만 발생해 "간헐적"으로 보였음.

**수정:** 클라이언트 타임아웃 30초 → 45초로 확대, 실패 시 서버가 알려주는 구체적 사유를 그대로 노출하도록 변경.

### 4-2. 주문취소 실패 사유 불투명 (`e509e27`)
취소 실패 시 항상 같은 문구만 표시되어 원인 파악이 불가능했던 것을, Manifest가 반환한 실제 에러 사유를 그대로 노출하도록 수정.

### 4-3. **체결된 주문이 계속 "미체결"로 표시되는 핵심 버그** (`fbefd65`, `0cd5645`)
**현상:** SOL을 70.5에 매도 주문 → 온체인 오더북에서는 이미 사라졌는데(=체결됨) 앱에서는 계속 "미체결 주문"으로 표시됨. 실측 확인 결과 지갑에 인출 가능한 USDT 0.191248개가 온체인에 대기 중이었음(자금은 안전, 미인출 상태였을 뿐).

**원인 (2단계):**
1. 체결 감지가 "주문 제출 트랜잭션 자체의 로그"에서만 fill 이벤트를 찾고 있었음 — 이 방식은 주문 제출 즉시 자기 자신과 크로스되어 체결되는 경우만 감지 가능하고, **일반적인 경우(나중에 다른 트레이더가 체결시키는 경우)는 fill 이벤트가 상대방 트랜잭션 로그에 기록되므로 절대 감지 불가능**했음.
2. 1차 수정 후 추가로 발견: 1시간 타임아웃 체크가 체결 여부 확인보다 먼저 실행돼서, 실제로 체결된 주문도 생성된 지 1시간이 지나면 체결 확인을 타보지도 못하고 곧바로 `expired` 처리됨.

**수정:**
- tx 로그 확인(즉시체결 감지) → 온체인 오더북 대조(다른 트레이더에 의한 체결 감지)까지 2단계로 체결 여부 확인
- 타임아웃은 체결 증거를 못 찾았을 때만 적용하도록 순서 변경
- 마켓 조회는 폴링(10초 주기) 1회당 캐시해 중복 RPC 방지

## 5. PIN 입력 UX 개선 (`66605ea`, `09bf271`)

**요청 배경:** 거래할 때마다 PIN을 매번 입력해야 해서 불편하다는 피드백.

- 지갑이 이미 잠금 해제된 세션이면 **매수/매도 주문, 주문취소, 스왑**은 PIN 모달 없이 즉시 서명/제출
- 잠겨있을 때(세션 최초 1회)만 PIN 모달 표시 → 이후 계속 유지
- **출금(수익 인출)은 특수 케이스로 유지** — 이미 잠금 해제된 상태여도 매번 PIN 재확인
- 거래 활동 시 5분 자동잠금 타이머를 연장하는 `extendSession()` 추가 (활발히 거래 중엔 타임아웃으로 끊기지 않도록)
- 탭 숨김 시 즉시 잠금, 5분 비활동 시 자동 잠금은 기존과 동일 유지 (보안 백스톱)
- 스왑과 외부 출금(`WithdrawModal`, 홈 화면 "출금")은 이번 변경 대상 아님 — 외부 출금은 기존과 동일하게 매번 PIN 필요

## 6. 지갑 중복 생성 버그 수정 (`bea3b94`)

**현상:** 모바일에서 지갑을 만든 후 PC로 접속(같은 텔레그램 계정)하면 기존 지갑 대신 완전히 새로운 지갑이 또 생성됨.

**원인:** 홈 화면이 "지갑 0개 → 지갑 생성 페이지로 이동"을 판단할 때, 서버 동기화(`fetchWallets`)가 끝나기도 전에 **이 기기의 로컬 저장소만 보고 판단**하는 레이스 컨디션이 있었음. 새 기기는 로컬에 지갑 정보가 없으므로 서버에 이미 지갑이 있어도 항상 "0개"로 오판해 즉시 지갑 생성 화면으로 보내버렸고, 설정 페이지도 URL 파라미터(`?create=true`)만 믿고 검증 없이 생성 모달을 띄웠음.

**수정:** `walletsSynced` 플래그를 추가해 서버 동기화가 실제로 끝난 뒤에만 "지갑 0개" 판단을 내리도록 홈 화면·설정 페이지 양쪽에 이중 확인 추가.

> 참고: 텔레그램 ID(`telegram_uid`)는 DB에서 UNIQUE 제약이라 동일 ID로 재로그인해도 **유저 계정 자체가 중복 생성되지는 않음** — 이번에 실제로 중복됐던 건 계정이 아니라 지갑(로컬 키페어)이었음.

## 7. 신규 상장 토큰 거래 실패 근본 원인 수정 (`cf6811c` ~ `bc03fee`)

**현상:** 신규 상장 토큰(DUDE) 매도 시도 시 "트랜잭션 생성에 실패했습니다" → 이후 "거래 준비가 아직 반영되지 않았습니다. 잠시 후 다시 시도해주세요" 반복 → "거래소가 아직 이 토큰의 마켓 정보를 인식하지 못했습니다" 순으로 계속 실패.

원인은 서로 다른 두 가지가 순서대로 겹쳐 있었음. **DUDE 토큰 자체의 문제가 아니라, 신규 상장 토큰에서 처음 발생하는 계정 상태(지갑별) 문제였음** — 최종적으로 SOL/USDT 마켓에서도 동일 지갑이 똑같이 실패하는 것을 확인해 DUDE 전용 문제가 아님을 검증함.

### 7-1. Manifest Global 계정 미생성 (`cf6811c`)
**원인:** Manifest는 민트마다 "Global 계정"(PDA)이 있어야 주문 생성 API가 동작하는데, 신규 상장 토큰은 이게 아직 없어 API가 항상 500으로 실패. Global 계정은 사용자 서명이 있어야 생성 가능.

**수정:** 주문 생성 전 Global 계정 존재 여부를 확인(`findMissingGlobalMints`)해, 없으면 생성 트랜잭션을 먼저 클라이언트에 반환(`setupRequired: true`) → 사용자 서명·제출 → 주문 재요청 시 정상 진행되는 흐름 추가. SOL 부족으로 생성 트랜잭션 시뮬레이션이 실패하면 필요 금액을 구체적으로 안내(`3321bab`).

### 7-2. `finalized` commitment로 인한 재시도 실패 (`8196e18`)
**원인:** 위 setup 트랜잭션을 컨펌까지 기다린 뒤 재시도해도, 서버의 RPC 커넥션이 기본값 `finalized` 커밋먼트를 쓰고 있어 방금 만든 계정이 최대 30초간 "아직 없음"으로 보임 → 재시도가 계속 setup을 또 요구하는 무한루프.

**수정:** Global 계정 조회에 `'confirmed'` 커밋먼트를 명시.

### 7-3. 마켓 좌석(seat) 미보유 시 500 에러 (`bc03fee`) — 진짜 근본 원인
**원인:** Manifest 주문 생성 API(`/v1/orders`)는 `setupIxs:true`를 줘도, 트레이더가 해당 마켓에 **좌석(seat)**이 없으면 스스로 만들지 못하고 `Cannot read properties of null (reading 'publicKey')` 500 에러를 냄 (거래소 쪽 버그로 추정). 좌석은 Global 계정과 달리 **지갑×마켓 조합마다 개인이 각자 보유**해야 하는 계정.

**실측 검증:** 동일한 SOL/USDT 마켓에서 좌석 없는 지갑(mayersam) → 500 / 좌석 있는 지갑(Kmkill) → 200 정상. DUDE와 무관하게 재현되어 "특정 토큰 문제"가 아님을 확정.

**수정:**
- `getMarketSeatSetup()` 추가 — `ManifestClient.getSetupIxs()`로 좌석 필요 여부 확인
- 필요 시 좌석 생성 instruction을 기존 setup 트랜잭션(ATA/Global 생성과 동일 트랜잭션)에 함께 포함, wrapper 키페어는 서버가 미리 서명(pre-sign)
- 커넥션 전체의 기본 commitment를 `'confirmed'`로 변경 (7-2와 동일한 원리의 재발 방지)

**비용 (실측, mayersam의 좌석 생성 트랜잭션 기준):**

| 항목 | 비용 | 부담 주체 |
|---|---|---|
| Global 계정 (민트당 1개, 전원 공유) | 약 0.0016 SOL | 그 토큰의 진짜 최초 거래자 1명 |
| 마켓 좌석 (지갑×마켓별 1개, 개인 소유) | 0.000673 SOL (렌트 668,160 + 수수료 5,000 lamports) | 그 마켓 첫 거래하는 사람 본인 |

이제 신규 토큰 상장이든 기존 토큰에 신규 유저가 진입하는 경우든, 위 두 상황 모두 `createOrder` 흐름 안에서 자동 감지 → 준비 트랜잭션 서명 요청 → 재시도로 자동 처리되어 추가 개입이 필요 없음.
